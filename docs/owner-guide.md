# Инструкция владельца продукта (TG Naydi)

Эта инструкция написана простым языком для владельца продукта без опыта программирования. Здесь описано, как проверять работу сайта, откатывать неудачный релиз за 1 минуту, подключить бесплатное хранилище Upstash Redis и (когда будете готовы) включить живую проверку через Telegram.

---

## 1. Как проверить, что сайт работает правильно

1. Откройте ваш публичный адрес на Vercel (`https://<ваш-проект>.vercel.app`).
2. Проверьте бейдж в правом верхнем углу:
   - **`ДЕМО-РЕЖИМ (SANDBOX)`** — безопасный режим проверки и демонстрации. Живой Telegram-аккаунт не используется, в выгруженном файле `result.csv` стоит отметка `SANDBOX`.
   - **`LIVE MTProto · Воркер онлайн`** — боевой режим проверки через ваш отдельный Telegram-аккаунт.
3. Нажмите кнопку **«Пример (Контакты Казани.csv)»** → **«Запустить проверку»**.
4. Во время работы нажмите **«Пауза»**, обновите страницу (`F5`) и убедитесь, что прогресс сохранился, затем нажмите **«Продолжить»**.
5. Нажмите **«Скачать result.csv (Excel)»** и откройте файл в Excel: русские подписи (`человек`, `канал`, `не найден / скрыт`) должны читаться без искажений, а счётчики в карточке должны сходиться со строками файла.
6. Проверка здоровья сервера: откройте `/api/health` (кнопка **«Статус»** в правом верхнем углу). В ответе должно быть `"status": "ok"` и `"storageMode": "upstash"` (на Vercel).

---

## 2. Как откатить неудачный релиз на Vercel за 1 минуту

Если после обновления сайт стал работать с ошибкой, вы можете вернуть предыдущую рабочую версию **без программиста**:

### Вариант А — в браузере (1 клик)
1. Откройте [vercel.com](https://vercel.com) → ваш проект **TG Naydi** → вкладка **Deployments**.
2. Найдите предыдущий зелёный релиз (`Ready`) → нажмите `...` (три точки справа) → **Instant Rollback**.
3. Через 5–10 секунд откройте `/api/health` и убедитесь, что `"status": "ok"` и вернулся предыдущий `commitSha`.

### Вариант Б — одной командой в терминале
```powershell
pnpm dlx vercel rollback
```

## 3. Как подключить бесплатное хранилище Upstash Redis (0 \$/мес)

На Vercel нет собственного жёсткого диска, поэтому для сохранения прогресса после `F5` нужен **Upstash Redis** (бесплатный тариф — до 500 000 операций в месяц, базы автоматически удаляются через 24 часа):

1. В панели вашего проекта на Vercel откройте **Storage** → **Create Database** → выберите **Upstash Redis** (бесплатный план **Free**).
2. Нажмите **Connect to Project** — Vercel сам добавит две переменные окружения:
   - `UPSTASH_REDIS_REST_URL`
   - `UPSTASH_REDIS_REST_TOKEN`
3. Сделайте **Redeploy** последнего деплоя. После этого жёлтое предупреждение исчезнет, а `/api/health` покажет `"storageMode": "upstash"`.

## 4. Как безопасно включить живую проверку через Telegram (когда будете готовы)

> **Важно:** никогда не используйте свой личный основной аккаунт Telegram. Заведите отдельный технический аккаунт и соблюдайте паузы (`>= 15 секунд` между пачками), чтобы избежать `FLOOD_WAIT` и ограничений Telegram.

1. Получите `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` на официальном портале `https://my.telegram.org` (раздел **API development tools**).
2. В настройках проекта на Vercel (**Settings → Environment Variables**) добавьте:
   - `PROVIDER_MODE=LIVE_MTPROTO`
   - `NEXT_PUBLIC_PROVIDER_MODE=LIVE_MTPROTO`
   - `OPERATOR_ACCESS_KEY=<придумайте длинный секретный пароль>` — **обязательно!** Этот пароль не даст случайным посетителям с интернета запускать проверки на вашем Telegram-аккаунте.
3. Запустите отдельный воркер `worker/mtproto.ts` на минимальном VPS (или локально) с теми же переменными `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` и вашими секретами `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_SESSION`:
   ```bash
   pnpm run worker:mtproto
   ```
4. Как только воркер запустится, бейдж на сайте автоматически покажет **`LIVE MTProto · Воркер онлайн`**.

## 5. Как работает автоматический контроль качества (AI-native SDLC)

- Все изменения попадают в `main` только через проверку (`pnpm run check`, 15 авто-проверок `eval:domain`, браузерный тест Playwright и сканер утечек секретов `gitleaks`).
- Автоматический мониторинг (`.github/workflows/monitoring.yml`) опрашивает `/api/health` и при аномальном росте ошибок сам открывает Pull Request с новым файлом постановки `docs/sdlc/incidents/intent-INC-*.md` — вы всегда видите проблему до того, как о ней напишут клиенты.
